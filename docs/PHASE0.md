# Sentinel Phase 0: Architecture, Data Inventory, Hypotheses, Risks

Status: proposal for approval. No code exists. No empirical result exists, and none will appear in any document unless the code in this repo computed it.

Writing convention for all docs: plain text, no em-dashes, no quotation marks.

## 1. Purpose and honest framing

Sentinel researches behavioral signals, converts them into a portfolio, stress tests the portfolio, and monitors it as if live, using only free data. The primary deliverable is a defensible research process, not a headline Sharpe ratio. The most likely honest outcome on free data is that several signals are weak or negative after costs. The platform is designed so that a null result is a clean, documented result.

Relation to the existing repo behavioral-pricing-kernel: that repo targets a pricing kernel study and reads WRDS credentials from the environment. Sentinel must not depend on it, because WRDS data cannot be required. See question 1.

## 2. Architecture

    free sources ──> ingest adapters ──> raw parquet (immutable, hashed)
                                              │
                                   pandera validation + PIT alignment
                                              │
                                      curated parquet (versioned)
                                              │
        ┌──────────────┬──────────────────────┴───────────────┐
     signals        factors/regimes                      universe/PIT
   (z-scored,      (FF, AQR, HMM)                     (constituents,
    lagged)                                             delistings)
        └──────────────┴──────────────┬───────────────────────┘
                                      │
                      backtest engine (event-aware, costs, borrow)
                         walk-forward, purged k-fold, DSR, holdout
                                      │
                      portfolio construction (MV-LW, leg-wise RP, leg-wise HRP)
                                      │
                    risk engine (VaR/ES, Kupiec, Christoffersen,
                       regimes, factor decomposition, stress)
                                      │
             ┌────────────────────────┼──────────────────────┐
         Streamlit               FastAPI service       PDF tear sheet
         dashboard           (signals, weights, risk)     (ReportLab)

Design principles:

1. Layers talk through typed parquet tables with pandera schemas. No module reads another module internals.
2. Every table carries two timestamps: event_date (what it describes) and available_date (when a trader could have known it). All joins use available_date. This is the single control for look-ahead.
3. Every signal is computed from data with available_date strictly before the trade date, and a unit test shuffles future data and asserts the signal does not change.
4. Raw data is write-once and content-hashed. Curated data is rebuilt from raw by one command.
5. One YAML config fully determines a run. Seeds are explicit. Run output directories are named by config hash.
6. Optional private adapters (WRDS, CRSP, OptionMetrics, Bloomberg) implement the same DataSource protocol, live in a gitignored private_adapters directory, and are never imported by core or CI.
7. Every reported number is written by code into results/ as JSON or CSV with the git SHA and config hash. Docs and the tear sheet read those files. A doc check in CI fails if a number in the docs has no source file.

Technology choices:

- Python 3.11, pandas, numpy, scipy, statsmodels, scikit-learn (Ledoit-Wolf), pyarrow, pandera, pydantic v2, typer, structlog, PyYAML.
- Regimes via statsmodels MarkovRegression first (one fewer fragile dependency than hmmlearn); hmmlearn as an optional comparison.
- Portfolio: own implementations of the equal risk contribution rule and the hierarchical allocation (used leg-wise as leg-wise risk parity and leg-wise HRP), checked against closed forms; cvxpy only if constrained MV needs it (open source, free).
- Reporting: Streamlit, plotly, ReportLab (pure Python, no system dependencies, so CI and Docker stay simple). WeasyPrint rejected for system library overhead.
- Quality: ruff, black, mypy strict on core, pytest, pytest-cov, hypothesis, pre-commit.
- Infra: Docker, docker-compose, GitHub Actions, Makefile.
- Paper: Markdown plus LaTeX build with tectonic, with figures generated by the same code.

Sample data policy (revised by decision D4): committed fixtures are synthetic and stay under 5 MB. No Yahoo derived data is published anywhere, including Releases and Hugging Face. Published artifacts are code, config, and derived results.

## 5. Ranked behavioral hypotheses

Ranking is by prior evidence strength, testability on free data, and expected survival after costs. All are pre-registered here, before any data is touched. Sign is the expected sign of the cross-sectional relation between signal and next period return.

| Rank | Signal | Expected sign | Rationale | Free data testable | Expected cost survival |
|---|---|---|---|---|---|
| 1 | MAX lottery preference: mean of top 5 daily returns in the past month (Bali, Cakici, Whitelaw 2011) | Negative | Investors overpay for lottery payoffs, so high MAX stocks are overpriced. Limits to arbitrage via short constraints. | Yes, prices only | Moderate. Concentrated in small illiquid names, so weaker in an S and P 500 universe. |
| 2 | 52 week high anchoring (George and Hwang 2004) | Positive | Investors anchor on the 52 week high and underreact to good news for stocks near it. | Yes, prices only | Moderate. Low turnover. |
| 3 | Short term reversal and overreaction: prior month return (Jegadeesh 1990) | Negative | Overreaction and liquidity provision. Decays within days. | Yes | Poor. Very high turnover, likely killed by costs. Included as a cost honesty case. |
| 4 | Capital gains overhang, disposition effect proxy (Grinblatt and Han 2005) using a volume weighted reference price from OHLCV | Positive | Investors hold losers and sell winners, so unrealized gains create selling pressure that depresses price, and prices later drift up toward fundamentals. | Yes, approximated. Reference price needs turnover, an imperfect proxy. | Moderate to poor. |
| 5 | Realized skewness from daily returns (Amaya et al 2015) | Negative | Same lottery preference channel, measured from skewness. Used as a backtestable stand in for option implied skew. | Yes | Moderate. |
| 6 | Abnormal attention: abnormal volume and, where available, Google Trends abnormal search volume (Da, Engelberg, Gao 2011; Barber and Odean 2008) | Positive then reversal | Attention driven retail buying pushes prices up, then reverses. Horizon matters. | Volume yes. Trends only for a small universe and short history. | Poor to moderate. |
| 7 | News tone from GDELT (Tetlock 2007 style) | Positive short horizon | Sentiment is slowly incorporated. Free tone data is noisy and entity matching is error prone. | Partially, 2015 onward, coarse | Poor. Likely weak. |
| 8 | Option implied skew or risk neutral density tilt (Xing, Zhang, Zhao 2010) | Negative | Informed traders buy puts, so steep skew predicts low returns. | Not backtestable on free data: CBOE has no history. | Unknown |

Proposed deviations from the brief, for approval:

- Analyst herding is dropped from the signal set. Free sources have no analyst forecast history (I/B/E/S is licensed). yfinance recommendation data has no reliable point in time history, so any signal built on it would be look-ahead contaminated. It is replaced by 52 week high anchoring. The gap is documented in LIMITATIONS.md and the private adapter interface leaves a slot for it.
- Option implied skew is built as a forward collection pipeline plus an SPX level analysis only, labeled not backtested. The cross sectional version is reported as untested until at least a year of snapshots exists. Realized skewness (rank 5) is the backtestable substitute.
- Result: six backtestable signals (ranks 1 to 6, with rank 7 as a seventh of lower quality), one forward only signal. This meets the six signal requirement without inventing data.

Per signal deliverable (Phase 2): hypothesis, construction, IC and rank IC by horizon, decay curve, turnover, capacity estimate from average dollar volume with a stated participation cap, orthogonalization against FF5 plus momentum, and a MODEL_CARD.

Multiple testing: the number of signals, horizons, and parameter variants tried is logged to a trial registry. Deflated Sharpe uses that count. Parameter grids are fixed in the pre-registration, not tuned.

## 6. Validation and leakage controls (planned)

- Holdout: the final segment of data is locked by a config hash. A guard raises an error on a second read. The run that touches it is recorded in the repo. See question 3 for the dates.
- Walk forward and purged k-fold with embargo sized to the longest label horizon.
- Leakage tests: shuffle future data, perturb post trade date rows, compare signals. Also a placebo test: signals built on randomly permuted tickers must show zero IC within noise.
- Too good to be true checklist: any Sharpe above 1 after costs triggers a mandatory leakage review before it is reported.
- Costs: commission, half spread proxy from a high low estimator, square root impact model with participation cap, and borrow cost. Free borrow data does not exist, so borrow cost is a flat assumed schedule by size bucket, labeled as an assumption, with sensitivity analysis.

## 7. The three biggest risks to the project

1. Survivorship and point in time universe bias. Yahoo has no delisted tickers. Even with a historical constituent list, prices for removed names are mostly missing, which biases returns upward, most severely for short legs and for reversal and lottery signals, where the losers are exactly the names that vanish. Mitigation: construct the universe from the constituent change log, measure and report the fraction of historical members with missing prices per year, run sensitivity analysis (drop periods with high missingness, impose a delisting return assumption), and state in LIMITATIONS.md that all alpha estimates are upper bounds. This cannot be fully fixed on free data.
2. Statistical power and data snooping. A free data, large cap, post 2005 sample gives modest power, and most published behavioral anomalies have decayed since publication. With six or more signals, several horizons, and several portfolio methods, a spurious winner is likely. Mitigation: pre-registration, trial counting, deflated Sharpe, a one time holdout, and a readiness to publish a null result. The risk is also reputational: a polished platform wrapped around a fragile alpha claim is worse than an honest null.
3. Scope and source fragility. Seven modules plus paper, API, and dashboard is a large surface for one builder, and several sources (yfinance, pytrends, CBOE, AQR files) are unofficial or change format. A reproducibility claim fails if a source breaks. Mitigation: gates between phases, a local rebuild script with a data manifest (row counts and content hashes) so a rebuild can be checked against the original run, public caches only for redistributable sources, source adapters with contract tests, graceful degradation for pytrends and CBOE, and a ruthless cut list (dashboard polish and Monte Carlo extras go before correctness work).

A secondary risk, now resolved by decision D4: no Yahoo derived data is redistributed.

## 8. Assumptions and what could be wrong (Phase 0)

- Assumption: adjusted close from yfinance is adequate for returns. Could be wrong: retroactive adjustment and occasional bad splits. Test: cross check a sample against Fama-French portfolio returns and flag outlier daily moves.
- Assumption: Wikipedia change log is complete enough. Could be wrong: gaps and name changes. Test: reconcile constituent count to roughly 500 each month.
- Assumption: EDGAR filing dates are a valid available_date. Could be wrong for amendments. Test: use first filing date only.
- Assumption: S and P 500 universe is liquid enough that costs are tractable. Could be wrong for the short leg of lottery signals.
- Nothing has been tested yet. Phase 0 is documents only.

## 10. Decision log (sponsor answers)

- D1. Sentinel is standalone and never imports behavioral-pricing-kernel. The README links to it as related work. A free-data option implied signal may be added later once forward collection has enough history.
- D2. Universe is the S and P 500 with point in time membership. The per-year missing-price measurement and sensitivity checks are a required Phase 1 deliverable.
- D3. Development window is 2005 to 2022. The holdout starts 2023-01 and ends on a fixed date written into configs/holdout.yaml on the day it is locked, so it does not drift. GDELT tone is evaluated only on its available sample and labeled short-sample.
- D4. CI uses synthetic data. A local script rebuilds real caches. No Yahoo derived data is published. Only redistributable sources are cached publicly.
- D5. Approved deviations from the original brief: analyst herding is replaced by 52 week high anchoring, and option implied skew is forward-only with realized skewness as the backtestable substitute. Both are documented as deviations in the README and the paper.
- D6. Long-short is the primary variant with a flat borrow cost assumption (labeled an assumption) and a sensitivity grid over several borrow levels. A long-only variant is also reported.
- D7. Forward collection is kept minimal. Raw CBOE snapshots are stored outside the public repo unless terms clearly allow redistribution. Only derived metrics are published. A keepalive prevents GitHub from disabling the schedule after 60 days of inactivity.
- D8. MIT license. Hours per week: 10. Cut order if time runs short: API, then forward collection, then dashboard polish. Never cut the data layer, signal validation, backtest rigor, or the risk engine.
